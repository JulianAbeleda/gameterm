# GameTerm Scene Mode Arkey Capability Routing Scope

Status: scoped, not implemented.

This document scopes how GameTerm can use an Arkey-style per-turn routing
substrate so Codex can know which GameTerm features are available without
pretraining, magic prompts, or unrestricted desktop automation.

The immediate motivation is desktop app tiling:

```text
open Safari
tile Firefox next to gameterm
open Spotify on the right
```

But the substrate should apply to all Scene Mode capabilities:

- compose backend selection
- fake Codex dogfood mode
- TTS/STT controls
- app tiling
- workspace/process discovery
- command actions
- file open actions
- future RPG/VN/game-state actions

## Core Claim

Arkey can provide the routing substrate, but GameTerm must remain the authority
for capability definitions, policy, approval, and execution.

Correct boundary:

```text
Arkey-style router
-> decides intent, relevant context, and likely capability family

GameTerm capability registry
-> defines what actions actually exist

GameTerm policy layer
-> validates, gates, and asks approval

GameTerm executor
-> performs the side effect
```

Incorrect boundary:

```text
Arkey/LLM
-> invents or directly executes GameTerm features
```

The substrate should make Codex capability-aware, not capability-authoritative.

## Primitives

### Turn

A turn is one user request plus the state needed to answer it.

For Scene Mode compose, a turn includes:

- user text
- current workspace path
- current Scene view
- active compose backend
- current voice/debug state
- available scene actions
- capability manifest
- recent conversation state
- pending approvals

The turn is the right unit for capability injection because available features
can change by mode, config, platform permission, and debug state.

### Intent

Intent is the router's best classification of what the user is trying to do.

Examples:

```text
"open Safari"
-> desktop_app_tiling

"turn on fake codex"
-> debug_compose_backend_toggle

"use the mic"
-> voice_input

"run tests"
-> workspace_command

"make Kiki bigger"
-> scene_visual_config
```

Intent is advisory. It narrows which capability manifests are shown to the LLM.
It does not execute anything.

### Capability

A capability is a named thing GameTerm can do.

Examples:

```json
{
  "id": "open_app_tile",
  "description": "Open or activate an allowlisted macOS app and tile it beside GameTerm.",
  "arguments": {
    "app_id": ["safari", "firefox", "spotify"],
    "external_layout": ["right_half"],
    "gameterm_layout": ["left_half"]
  },
  "risk": "external_app",
  "requires_confirmation": true
}
```

Capabilities are generated by GameTerm from Rust-owned config and runtime state.
They are not free-text memories.

### Action Proposal

An action proposal is structured output from Codex.

Example:

```json
{
  "type": "open_app_tile",
  "app_id": "safari",
  "external_layout": "right_half",
  "gameterm_layout": "left_half"
}
```

The proposal is not execution. It is a request for GameTerm to validate and
possibly present an approval choice.

### Policy

Policy decides whether a proposed action is allowed.

Policy checks:

- capability exists
- argument values are known
- app is allowlisted
- platform is supported
- required permissions are present
- action risk is acceptable
- confirmation has happened when required

Policy is deterministic Rust logic. It must not rely on the LLM's wording.

### Approval

Approval is the user-facing step before an external side effect.

Scene Mode should model approval like a visual novel choice:

```text
> Open Safari on the right
  Cancel
```

Approval should produce a second internal event:

```text
approval_granted(open_app_tile)
```

Only then should execution run.

### Executor

The executor performs the side effect.

Examples:

- launch Safari
- move GameTerm's window
- move Safari's window
- switch compose backend
- start fake Codex mode
- run TTS test
- run a workspace command

The executor reports a structured result back to Scene Mode.

### Capability Manifest

The capability manifest is compact runtime context inserted into the compose
prompt.

Example:

```json
{
  "version": 1,
  "turn_intent": "desktop_app_tiling",
  "capabilities": [
    {
      "id": "open_app_tile",
      "risk": "external_app",
      "requires_confirmation": true,
      "args": {
        "app_id": ["safari", "firefox", "spotify"],
        "external_layout": ["right_half"],
        "gameterm_layout": ["left_half"]
      }
    }
  ]
}
```

The manifest should be concise enough to include every turn, or routed down to
the relevant subset when the registry grows.

## Relationship To Arkey v2

The local Arkey v2 Rust runtime already has useful pieces:

- per-turn preflight
- framework/routing detection
- payload construction
- runtime state
- response logging and audits

GameTerm should reuse the product idea, not blindly embed the whole Arkey
runtime.

Useful Arkey-shaped concepts:

- `preflight`: derive turn context before model dispatch
- `payload`: build the exact model input from structured state
- `framework_hits`: use scoring/routing results as advisory context
- `manifest`: write inspectable JSON evidence for what was injected
- `post_turn`: audit what happened after the response

GameTerm equivalent:

```text
Scene compose submit
-> SceneCapabilityPreflight
-> SceneCapabilityManifest
-> compose prompt construction
-> Codex response parser
-> proposed actions
-> policy validation
-> approval choice
-> executor
-> result patch/dialogue/status
-> audit/debug report
```

## Product End State

The first pass is complete when:

1. GameTerm has a Rust-owned capability registry for Scene Mode.
2. Each capability has an id, description, argument schema, risk level, policy
   metadata, and enabled/disabled reason.
3. Scene compose builds a per-turn capability manifest.
4. The manifest is visible in the Scene debug menu or diagnostics.
5. Codex receives capability instructions in the compose prompt.
6. Codex can propose structured actions, but cannot execute them directly.
7. GameTerm validates every proposed action against the registry and policy.
8. Risky actions become VN-style approval choices.
9. Approved actions execute through typed Rust executors.
10. Action results are rendered in dialogue/status without closing Scene Mode.
11. Tests prove the router cannot bypass disabled capabilities or approval.

## Non-Goals

- No unrestricted desktop automation.
- No global "Codex can do anything GameTerm can do" mode.
- No direct LLM execution of shell/app actions.
- No hidden feature injection without diagnostics.
- No importing Arkey's private/personal mind data into GameTerm.
- No dependency on Arkey framework files for GameTerm product behavior.
- No cross-platform app tiling in the first pass.
- No replacement of Scene Mode action validation.

## Architecture

### Layer 1: Capability Registry

Add a Scene capability registry that can produce typed descriptors.

Candidate Rust model:

```rust
pub struct SceneCapabilityDescriptor {
    pub id: SceneCapabilityId,
    pub label: String,
    pub description: String,
    pub risk: SceneCapabilityRisk,
    pub requires_confirmation: bool,
    pub args: Vec<SceneCapabilityArg>,
    pub enabled: bool,
    pub disabled_reason: Option<String>,
}
```

Candidate capability ids:

```text
open_app_tile
run_command
open_file
toggle_fake_codex
set_compose_backend
run_voice_test
set_voice_backend
set_vn_layout_param
set_vn_asset_binding
```

First implementation should only wire a small subset:

- `toggle_fake_codex`
- `set_compose_backend`
- `run_voice_test`
- `open_app_tile` as scoped/proposed, with execution allowed only when the app
  tiling implementation lands

### Layer 2: Intent Router

The first-pass router can be deterministic and small.

It should classify prompts into capability families using simple rules:

```text
open/tile/safari/firefox/spotify -> desktop_app_tiling
fake codex/debug backend          -> compose_debug
voice/mic/tts/stt/test voice      -> voice
run/test/build/cargo              -> workspace_command
layout/opacity/font/box           -> scene_visual_config
```

This is enough to avoid showing every capability every turn.

Later, this can use richer Arkey-style scoring:

- keyword score
- active mode score
- recent turn score
- explicit command score
- failed-action retry score

The router returns:

```rust
pub struct SceneTurnRoute {
    pub intent: SceneTurnIntent,
    pub confidence: SceneRouteConfidence,
    pub capability_ids: Vec<SceneCapabilityId>,
    pub evidence: Vec<String>,
}
```

### Layer 3: Capability Manifest Builder

Build a compact manifest for the selected capabilities.

Rules:

- include only enabled capabilities by default
- include disabled capabilities only when useful for diagnostics
- include allowed enum values
- include required confirmation
- include "do not claim execution" instruction
- cap output length

### Layer 4: Prompt Contract

Compose prompt gets a section like:

```text
GameTerm capabilities available this turn:
{manifest}

If a capability is relevant, propose it using structured JSON.
Do not say it ran. GameTerm will validate, ask approval if needed, and report
the result.
```

The model can return:

```json
{
  "speaker": "Codex",
  "text": "I can open Safari beside GameTerm.",
  "actions": [
    {
      "type": "open_app_tile",
      "app_id": "safari",
      "external_layout": "right_half",
      "gameterm_layout": "left_half"
    }
  ]
}
```

### Layer 5: Parser And Validator

Parse proposed actions from Codex output into typed proposals.

Validation must reject:

- unknown capability id
- disabled capability
- unknown argument
- unknown enum value
- missing required argument
- action that requires confirmation but is marked as already executed
- any proposal that asks to run shell/AppleScript outside the typed executor

### Layer 6: Approval Choice

Risky validated proposals should become choices in Scene Mode.

Example:

```text
Codex
I can open Safari beside GameTerm.

> Open Safari on the right
  Cancel
```

The approval choice should carry the validated action object internally.
It should not reparse the visible label.

### Layer 7: Executor

The executor should consume only validated, approved actions.

Execution output:

```rust
pub enum SceneCapabilityExecutionResult {
    Succeeded { message: String },
    Failed { message: String, diagnostics: Vec<String> },
    NotImplemented { message: String },
}
```

For the substrate pass, `open_app_tile` can return `NotImplemented` while still
proving routing, proposal, validation, approval, and diagnostics.

For the app-tiling pass, `open_app_tile` gets a native macOS executor.

## Capability Families

### Desktop App Tiling

Intent:

```text
open Safari
tile Firefox beside this
put Spotify on the right
```

Capabilities:

- `open_app_tile`

Policy:

- app allowlist
- macOS platform
- Accessibility permission diagnostic
- confirmation required

### Compose Backend Control

Intent:

```text
use fake codex
turn fake codex off
switch back to real codex
```

Capabilities:

- `toggle_fake_codex`
- `set_compose_backend`

Policy:

- local debug action
- confirmation optional
- should clear dialogue when toggling fake mode if product behavior requires it

### Voice Debug And Test

Intent:

```text
test voice
is the mic working
run TTS test
```

Capabilities:

- `run_voice_test`
- `set_voice_backend`
- `set_microphone`

Policy:

- no external app automation
- uses configured local tools
- diagnostic result visible in debug menu

### Workspace Command

Intent:

```text
run tests
cargo check
build the app
```

Capabilities:

- `run_command`

Policy:

- existing command policy remains authoritative
- explicit argv/cwd
- confirmation based on risk

### Scene Visual Config

Intent:

```text
make the dialogue font bigger
lower the opacity
move the composer box
```

Capabilities:

- `set_vn_layout_param`
- `set_vn_asset_binding`

Policy:

- config action
- no shell
- writes only approved config file

## Data Flow

```text
User submits compose text
        |
        v
SceneTurnRouter
        |
        v
Capability registry filters relevant descriptors
        |
        v
SceneCapabilityManifest is generated
        |
        v
Compose prompt includes manifest + output contract
        |
        v
Codex returns dialogue + proposed actions
        |
        v
GameTerm parses proposed actions
        |
        v
Policy validator accepts/rejects
        |
        v
If risky: VN-style approval choice
        |
        v
Executor runs approved action
        |
        v
Scene dialogue/status/debug report result
```

## Debug Surface

The debug menu should show:

- detected turn intent
- selected capability ids
- enabled capabilities
- disabled capabilities with reasons
- last prompt manifest preview
- parsed action proposals
- policy decision
- approval state
- execution result

This is important because capability routing is otherwise invisible. If Codex
does not propose the expected action, the user needs to know whether the
problem was:

- router did not select the capability
- capability was disabled
- prompt manifest was wrong
- Codex ignored the manifest
- parser rejected JSON
- policy blocked it
- approval was missing
- executor failed

## Test Plan

### Unit Tests

Capability registry:

- lists expected first-pass capabilities
- marks disabled capabilities with clear reasons
- serializes a compact manifest
- excludes unknown capabilities

Router:

- `open Safari` routes to `desktop_app_tiling`
- `use fake codex` routes to `compose_debug`
- `test voice` routes to `voice`
- ambiguous prompts route to safe default with no risky capability

Prompt construction:

- includes only selected capability descriptors
- includes "do not claim execution" rule
- caps manifest length

Parser:

- parses valid action proposal JSON
- rejects unknown action types
- rejects unknown argument values
- rejects malformed JSON without crashing compose

Policy:

- blocks disabled capability
- blocks unknown app
- requires approval for external app tiling
- allows local debug toggle when enabled

Approval:

- proposal becomes a Scene choice
- cancel does not execute
- approval passes only the stored validated action

Executor:

- not-implemented executor reports a visible diagnostic
- execution result patches status/dialogue

### Integration Tests

Fake-Codex compose:

- fake backend returns an `open_app_tile` proposal
- Scene displays approval choice
- selecting cancel leaves no execution result
- selecting approve reaches executor and reports `NotImplemented` until tiling
  implementation lands

Debug menu:

- shows intent and selected capabilities
- shows policy block reason for unknown app
- shows parser failure for malformed action JSON

### Smoke Tests

First substrate smoke:

```text
GAMETERM_SCENE_COMPOSE_BACKEND=fake
scenario: ask "open Safari"
expect:
  dialogue says proposal
  approval choice appears
  debug menu shows desktop_app_tiling route
  approval result is visible
```

App tiling smoke after executor lands:

```text
ask "open Safari"
approve
expect:
  GameTerm left
  Safari right
  status reports success
```

## Implementation Lanes

### Lane 1: Registry And Types

Add typed capability descriptors and ids.

Deliverables:

- registry module
- serializable descriptors
- first-pass capability list
- unit tests

### Lane 2: Deterministic Router

Add a small per-turn intent router.

Deliverables:

- `SceneTurnIntent`
- `SceneTurnRoute`
- route evidence strings
- tests for app tiling, voice, debug backend, visual config, workspace command

### Lane 3: Manifest Injection

Build the manifest and inject it into Scene compose prompts.

Deliverables:

- manifest builder
- prompt section
- diagnostics/debug visibility
- tests for manifest content and caps

### Lane 4: Action Proposal Parser

Parse structured actions from compose output.

Deliverables:

- typed proposal model
- JSON parser
- failure diagnostics
- tests for valid/invalid proposals

### Lane 5: Policy And Approval

Validate proposals and turn risky actions into approval choices.

Deliverables:

- policy validator
- approval choice builder
- cancel/approve handling
- tests for action gating

### Lane 6: Executor Boundary

Add executor trait/boundary and stub implementation.

Deliverables:

- typed executor result
- `NotImplemented` path for `open_app_tile`

- tests for result rendering

### Lane 7: Debug Menu Integration

Surface routing and capability diagnostics in the existing Scene Mode debug
menu.

Deliverables:

- selected intent
- manifest preview
- parsed proposal list

### Lane 8: App Tiling Executor Follow-Up

Implement native macOS app tiling using the separate app-tiling scope.

Deliverables:

- allowlist config
- native macOS bridge
- Accessibility diagnostic
- real Safari smoke

## Definition Of Done

The capability-routing substrate is done when:

- GameTerm owns a typed capability registry.
- Scene compose performs a per-turn route before model dispatch.
- Codex receives a compact capability manifest.
- Proposed actions are parsed into typed data.
- Policy validation cannot be bypassed by model text.
- Risky actions become approval choices.
- Debug menu can explain why an action did or did not happen.
- Tests cover registry, routing, manifest, parser, policy, approval, and stub
  execution.
- App tiling remains scoped separately until native execution is implemented.

## Open Questions

1. Should disabled capabilities be included in the manifest with reasons, or
   hidden from Codex and shown only in debug diagnostics?
2. Should fake-Codex toggling be a capability proposal, a debug-menu-only
   action, or both?
3. Should app tiling approval be single-turn only, or can the user persist
   trust for an app/layout pair?
4. Should GameTerm keep a local capability history so Codex can learn which
   actions failed recently?
5. Should route evidence be visible in normal Scene Mode, debug only, or smoke
   reports only?

## Recommended First Implementation

Build the substrate before native app tiling:

1. registry
2. deterministic router
3. manifest injection
4. parser
5. policy
6. approval choices
7. stub executor
8. debug diagnostics

Then implement the actual macOS app-tiling executor as the next separate pass.

This keeps the "brain" layer honest: it can know and propose GameTerm features,
but GameTerm still owns the rules and side effects.
