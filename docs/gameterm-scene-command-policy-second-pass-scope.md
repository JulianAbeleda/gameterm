# GameTerm Scene Command Policy Second-Pass Scope

Status: implemented through Lane 7.

This document scopes the next meaningful Scene Mode product layer after the
first-pass roadmap was completed.

It combines the deferred parts of:

- [Command Selection Scope](gameterm-scene-command-selection-scope.md)
- [Policy Boundaries Scope](gameterm-scene-policy-boundaries-scope.md)

## Goal

Scene Mode should let a user quickly find the right action while understanding
where that action came from and what kind of permission/risk it carries.

The first pass grouped existing choices by action kind and added doctor
diagnostics for command shape. The second pass should make action selection and
action policy part of the same product model.

The user should be able to answer:

- What actions are available for the selected entity?
- Which actions came from authored scene JSON, workspace discovery, an agent,
  or runtime state?
- Which actions only inspect/open local state?
- Which actions can run a shell command?
- Why is an action blocked, hidden, or risky?
- What will happen if I press enter?

## Product End State

The second pass is complete when:

1. Existing scenes and choices remain valid.
2. Existing activation behavior remains explicit and user-driven.
3. Actions can carry origin and policy/risk metadata.
4. Generated workspace actions include deterministic origin/policy metadata.
5. Normal view or command-selection view shows action kind, origin, and policy
   concisely.
6. Users can filter or narrow actions by action kind, selected entity, text, or
   policy without executing anything.
7. `RunCommand` and future agent-proposed commands are visibly different from
   inspect/open/navigate actions.
8. Doctor reports missing or inconsistent command policy metadata.
9. Deterministic tests cover schema compatibility, rendering, filtering, and
   activation.
10. Live smoke is added only if input ownership, overlay behavior, or GUI
    rendering changes.

## Non-Goals

- No automatic command execution.
- No agent launch or model call.
- No shell-command allowlist enforcement in this pass.
- No security sandbox.
- No broad action-engine rewrite.
- No breaking rename of existing `choices`.
- No removal of the current normal-view grouped choices.
- No new app bundle or installer work.

## Current Baseline

Already implemented:

- `SceneActionKind` distinguishes `Inspect`, `OpenFile`, `RunCommand`,
  `Navigate`, `AdvanceDialogue`, `Resolve`, `ExportStoryState`, and
  `ImportStoryState`.
- Normal view groups choices by action kind.
- Selected choice activation uses the existing selected-choice index.
- `RunCommand` requires explicit argv and target.
- Doctor warns when `RunCommand` lacks cwd.
- Workspace Discovery writes cwd on generated verification commands.
- Docs state that discovery does not run commands, start agents, or submit
  prompts.

Second-pass additions now implemented:

- optional action origin/risk/scope policy metadata
- derived policy defaults for old scenes
- policy-aware normal view and Tile Debugger output
- doctor diagnostics for missing and mismatched policy metadata
- workspace-generated policy metadata
- derived command option rows and deterministic filtering helpers
- runtime command-selection view rendered by `gameterm-visual`

## Action Model

The second pass should introduce a small optional action metadata model while
preserving existing choices.

Candidate shape:

```json
{
  "label": "Run verification",
  "kind": {
    "RunCommand": {
      "argv": ["ci/gameterm-scene-verify.sh", "--all"],
      "cwd": "/Users/julianabeleda/env/gameterm",
      "target": "tab"
    }
  },
  "policy": {
    "origin": "workspace_discovery",
    "risk": "command",
    "scope": "workspace",
    "requires_confirmation": true,
    "summary": "Runs the explicit verifier in the discovered workspace"
  }
}
```

This model is optional. Scenes without `policy` should continue to load and
render.

### Origin

`origin` describes where an action came from:

- `authored`: hand-authored scene JSON or template
- `workspace_discovery`: generated by `ci/gameterm-scene-workspace.sh`
- `agent`: proposed by an agent or agent helper
- `runtime`: emitted by Scene runtime state
- `fixture`: fixture/test authored action
- `unknown`: fallback for omitted metadata

Rules:

- omitted origin renders as `unknown` or remains hidden in compact views
- generated helpers should write a concrete origin
- doctor should warn on unknown origin for generated command actions

### Risk

`risk` describes what activation can do:

- `inspect`: reads current scene/runtime state only
- `open_file`: asks the GUI/OS to open a local file
- `navigate`: loads another scene file
- `state_change`: mutates Scene runtime state only
- `story_io`: imports or exports story/session state
- `command`: runs an explicit command in a GameTerm pane/tab
- `agent_proposal`: represents work proposed by an agent, not auto-approved
- `unknown`: fallback for omitted metadata

Rules:

- `RunCommand` defaults to `command` if risk is omitted
- `OpenFile` defaults to `open_file`
- `Navigate` defaults to `navigate`
- `Resolve` defaults to `state_change`
- doctor should warn when explicit risk conflicts with action kind
- command-like risks must never imply automatic execution

### Scope

`scope` describes where the action applies:

- `scene`
- `selected_entity`
- `workspace`
- `pane`
- `process`
- `agent`
- `external`
- `unknown`

The first implementation can render scope without enforcing it.

### Summary

`summary` is optional human-readable text for command search and policy
display. It should be short, non-empty when present, and never replace the
structured action kind.

## Schema Strategy

Preferred first implementation:

- add optional `policy` to `SceneAction`
- derive default policy at render/debug time when omitted
- keep old scenes valid
- validate explicit policy only when present
- keep serialization clean with `skip_serializing_if`

Do not add a separate global command registry in the first slice. The existing
choice list is still the source of activation order.

Migration rule:

- old scenes with no policy metadata are compatible
- generated scenes may start writing policy metadata once validation and doctor
  coverage exist
- docs should say policy metadata informs display/diagnostics only until a
  future enforcement layer is explicitly scoped

## UI Shape

There are three viable UI shapes. Pick the smallest one that solves the second
pass.

### Option A: Policy-Aware Normal View

Keep the current grouped choices and add compact suffixes:

```text
[RunCommand]
> Run verification  origin=workspace_discovery risk=command scope=workspace
```

Pros:

- smallest implementation
- no new input ownership
- no live smoke required unless layout changes are large

Cons:

- does not solve text search
- can crowd small terminal windows

### Option B: Command Selection View

Add a Scene runtime view alongside `Scene` and `TileDebugger`:

```text
Command Selection
filter: <text>

RunCommand  command workspace  Run verification
OpenFile    open_file scene     Open task brief
Inspect     inspect selected   Inspect selected entity
```

Pros:

- supports filtering and richer policy display
- can keep normal view compact
- fits existing state-machine model

Cons:

- new input ownership
- more tests
- likely live smoke if key handling changes

### Option C: GUI Overlay

Build a separate overlay for command search.

Pros:

- richer UX later

Cons:

- too much surface for this pass
- overlaps existing overlay architecture
- likely distracts from policy model

Recommendation: implement Option A first only if policy metadata needs a quick
visible path. Otherwise scope Option B as the real second-pass UI and keep it
inside `gameterm-visual` before considering GUI overlay work.

## Filtering Model

Filtering must never execute actions.

First filtering dimensions:

- text: label, summary, action kind, origin, risk, scope
- selected entity: actions whose policy scope is `selected_entity` or whose
  conditions/metadata reference the selected entity
- action kind: `RunCommand`, `OpenFile`, etc.
- risk: show/hide `command`, `agent_proposal`, `unknown`

Initial implementation can be a deterministic runtime helper before a full UI:

- derive `VisualCommandOption` rows from choices
- expose rows in debug report or tests
- render rows in command-selection view only after the data model is stable

## Doctor And Validation

Validation should remain schema-focused:

- reject empty policy fields when present
- reject unknown `origin`, `risk`, or `scope`
- reject explicit risk/action-kind conflicts only if the mismatch is
  unambiguously wrong

Doctor should provide product diagnostics:

- warn when generated `RunCommand` lacks policy metadata
- warn when `RunCommand` lacks cwd
- warn when command risk is not `command`
- warn when `OpenFile` risk is not `open_file`
- warn when `agent_proposal` has no summary
- suggest adding cwd, origin, risk, or scope where useful

Doctor strict mode should fail on warnings, preserving existing behavior.

## Authoring And Helper Impact

Author helper:

- allow adding policy metadata to choices
- preserve existing `add-choice` and `update-choice` behavior when policy args
  are omitted
- validate policy values before writing

Workspace helper:

- write `origin=workspace_discovery`
- write risk based on action kind
- write `scope=workspace` for verification commands
- write `scope=scene` or `workspace` for generated file actions depending on
  the target
- write short summaries for generated commands and task brief actions

Agent helper:

- do not write executable commands in this pass
- if agent-proposed actions are added later, use `origin=agent` and
  `risk=agent_proposal`

## Rendering And Debug Impact

Normal view:

- continue grouped action headings
- show policy only when it is compact enough
- never hide command actions by default in the first rendering slice

Tile Debugger:

- show selected choice policy fields
- show filtered command count if command-selection view exists
- show whether policy was explicit or derived

Snapshot/debug APIs:

- add policy information only if tests need stable programmatic access
- avoid broad public API churn until the UI shape is selected

## Acceptance Criteria

Second pass is complete when:

- old fixtures and user scenes without policy still load
- generated workspace scenes include policy metadata
- doctor warns about missing or mismatched policy where appropriate
- normal/debug UI makes command actions visibly distinct from inspect/open
  actions
- filtering model exists, or the scope explicitly records why rendering-only
  policy is enough for this pass
- activation remains explicit and unchanged
- full verifier passes

Current status: implemented. The runtime command-selection view is intentionally
inside `gameterm-visual`; a separate GUI overlay remains deferred.

## Risks

Risk: schema metadata becomes policy theater.

Mitigation: keep clear language that policy metadata is diagnostic/display
only until enforcement is scoped.

Risk: command palette becomes a second overlay architecture.

Mitigation: start inside `gameterm-visual` runtime views before building GUI
overlay work.

Risk: action metadata bloats authored JSON.

Mitigation: make policy optional and let helpers generate it where useful.

Risk: policy names imply security guarantees.

Mitigation: use labels like `risk` and `origin`, not `safe`, `trusted`, or
`approved`, unless enforcement exists.

Risk: filtering changes activation order.

Mitigation: keep original choice indices and test selected-choice activation.

## Deferred Work

- command allowlists
- workspace command sandboxing
- agent-proposed command approval UI
- signed/trusted generated scenes
- policy inheritance from mode/layer
- GUI overlay command palette
- keyboard shortcut customization
- persistent command history

## Done Definition

The second-pass command policy layer is done when Scene Mode has a compatible,
tested action policy model and a visible command-selection surface that helps
users find actions and understand their origin/risk without changing explicit
activation semantics.
